Detailed Scoring Breakdown

1. Functionality 7/10

What works: The app successfully shortens URLs via POST /API/shorten, lists them via GET /API/list, and redirects via GET /{code}. The frontend provides a clean UI for interaction. Swagger is configured for API testing.

Issues:

  • No duplicate URL detection — same long URL creates a new short code every time
  • No custom alias support — codes are always random 6-char GUID substrings
  • No click tracking or analytics
  • No expiration/TTL for shortened URLs
  • The frontend "history" functions are stubbed out (empty functions)
  • No input validation on the server side beyond deserialization

2. Code Quality 5/10

Strengths: Clean separation of concerns with Controllers/Models/Data layers. Proper use of dependency injection. Async/await used in the shorten endpoint.

Weaknesses:

  • Typo in model name: UrlShrotner (should be UrlShortener) — this propagates to the DbSet and database table name
  • No service layer — business logic lives directly in controllers
  • No repository pattern or abstraction over DbContext
  • No DTOs / ViewModels — raw models exposed in API responses
  • No error handling middleware
  • Unused imports (e.g. System.Xml.Serialization in UrlController)
  • Leftover commented-out code in Program.cs (line 10)
  • No null checks on constructor-injected dependencies
  • Substring(0, 6) on a GUID is not a great short code strategy — can collide
  • The .gitignore is minimal (only ignores .vs/)

3. UI/UX 8/10

Strengths: Clean, modern dark-mode design. Responsive layout. Loading states on the button. Keyboard Enter support. Animated transitions. Copy-to-clipboard functionality. Great color palette and visual polish.

Issues:

  • No URL list/management UI (the API endpoint exists but isn't used in the frontend)
  • No history display despite the feature skeleton being present
  • No error state visualization (the card just shows a text status)
  • No URL validation preview (e.g. green checkmark when valid)

4. Security 5/10

Concerns:

  • Open Redirect vulnerability: The RedirectController takes any code and redirects to whatever URL is stored. An attacker who can insert a malicious URL gets a free open redirect from your domain.
  • No rate limiting on the /API/shorten endpoint
  • No URL validation on the server (malicious/internal URLs not filtered)
  • No HTTPS enforcement beyond the standard middleware
  • No authentication/authorization — anyone can shorten URLs and list all entries
  • SQLite DB file (urls.db) is not gitignored and lives in the project root
  • No input sanitization or size limits

5. Architecture 6/10

Strengths: Proper MVC structure. DI used correctly. Separate controllers for different concerns. Good use of EF Core migrations.

Weaknesses:

  • No service/business layer — controllers are heavyweight
  • No interface abstractions (programming to concrete DbContext)
  • No unit test project or test project structure
  • No configuration validation
  • The appsettings.json contains a connection string comment suggesting SQL Server but the code uses SQLite hardcoded in Program.cs
  • The connection string is hardcoded in Program.cs instead of reading from config
  • No logging beyond the default ASP.NET Core pipeline

Critical Issues to Fix

Open Redirect Vulnerability

The RedirectController blindly redirects to any URL stored in the database. Validate that the target URL is a safe, public URL — or at minimum implement a URL allowlist or require HTTPS-only.

Short Code Collision Risk

Using Guid.NewGuid().ToString().Substring(0, 6) (~2.8B possible values) is probably fine for small scale, but a database unique constraint or a collision check before insert would prevent rare duplicates.

Model Typo & DB Schema

UrlShrotner should be renamed to UrlShortener. This requires a new migration. Also, the ShortUrl column has no unique index — enabling one would prevent duplicate codes.

Missing .gitignore Entries

The bin/, obj/, *.db, and *.db-* files should be gitignored. The SQLite database and build artifacts are currently tracked.

Recommendations for v2.0

Short-term (Easy wins)

  • Fix model typo: UrlShrotner → UrlShortener
  • Add unique constraint on ShortUrl column
  • Read connection string from appsettings.json
  • Clean up unused imports and commented code
  • Improve .gitignore (bin/, obj/, *.db)
  • Add server-side URL validation
  • Wire up the frontend to the /API/list endpoint

Long-term (Structure)

  • Add a service layer (IUrlShortenerService)
  • Implement URL validation (allowlist or safety check)
  • Add rate limiting middleware
  • Add custom alias feature
  • Implement click tracking / analytics
  • Add authentication (API keys or user accounts)
  • Write unit tests & integration tests
  • Add request/response DTOs
  • Add URL expiration / TTL support
